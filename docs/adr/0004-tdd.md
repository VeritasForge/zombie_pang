# ADR 0004: TDD 3 카테고리 + Property-based + Mutation Testing 강제

- **Status**: Accepted
- **Date**: 2026-05-17
- **Deciders**: 글로벌 CLAUDE.md (3 카테고리 룰 원본) + Phase A-4 Research

---

## Context

좀비팡은 다음과 같은 특수한 테스트 요구사항이 있습니다.

1. **게임 도메인 규칙이 풍부** — Combo tier (×1 → ×1.5 → ×2 → ×3), spawn rate 곡선 (1000ms → 300ms), Boss HP 곡선 (1.0/1.5/2.25/3.10/3.84), Daily Streak (선형 +20%/일, 페널티 0) 등 경계값이 명시적으로 많음
2. **결정론 강제** — Layer 1 (좀비 처치, 콤보, Crit, Power-up drop rate, 카드 추첨)은 결정론. 같은 seed에서 같은 결과가 나와야 property-based 테스트에서 1000회 반복 검증 가능
3. **자율 실행** — Phase C는 사용자 개입 0회 가정. 테스트가 회귀 잡지 못하면 자율 주행 실패
4. **MVP 출시 가능 품질** — domain 100% line coverage 필요. mutation 점수로 "100% line 100% useless" 안티패턴 차단

---

## Decision

**3-Layer Test Strategy 전부 채택**

1. **TDD 3 카테고리 룰** (RED phase 강제)
2. **Property-based (fast-check 3.x + @fast-check/vitest)** — seed=42, numRuns=1000
3. **Mutation Testing (Stryker 8.x + vitest-runner)** — Domain ≥80%, Application ≥70%

### Testing Trophy (Kent C. Dodds)

```
            ┌──────────┐
           /    E2E     \      10% — Playwright (3 시나리오)
          /──────────────\
         / Integration    \    50% — adapters + use case (vitest-canvas-mock)
        /──────────────────\
       /       Unit         \  30% — domain + application
      /──────────────────────\
     /        Static          \ 10% — TypeScript strict + Biome
    └──────────────────────────┘
```

Test Pyramid가 아닌 **Testing Trophy** 채택 — 게임은 scene/use case 경계가 좁아 단위만으로는 회귀 잡기 어려움.

### 3 카테고리 룰 (글로벌 CLAUDE.md 원본)

| 카테고리 | 검증 대상 | 좀비팡 예시 |
|---------|----------|------------|
| `[Happy]` | 정상 흐름 | combo 5kill 후 ×1.5 / Power-up 정상 발동 / wave 10 도달 시 CEO 보스 등장 |
| `[Boundary]` | 경계 / 엣지 | combo decay 정확히 1500ms / spawn rate 하한 300ms / 도주 4→5 fail 경계 / streak 7→8 (상한+휴식) / Power-up 동시 활성 1→2→3 (한도) / freeze-frame 0/599/600/601ms / coin 0/1/9999 |
| `[Error]` | 예외 / 에러 | localStorage quota 초과 → graceful degrade / Vibration API 미지원 → no-op / RNG seed 미주입 → throw / 잘못된 power-up 타입 / negative score / 도주 누적 음수 |

**규칙**:
- Happy만 작성 후 GREEN 진입 금지 (RED에 3 카테고리 강제)
- 명시적으로 catch하는 모든 예외 타입 **각각** 1개 (`catch (StoreQuotaError | StoreUnavailableError)`이면 2개)
- 단순 보관 Task의 `[Error]` 부재는 PR/Task에 **사유 명시 필수**

### Property-based Invariant 7개

| # | Invariant | 도메인 |
|---|-----------|--------|
| 1 | `score ≥ 0` 항상 성립 | Score |
| 2 | Combo tier는 단조 증가하다 decay/miss에만 리셋 | Combo |
| 3 | `spawnRate(N ∈ [1,10]) ∈ [300, 1000]` ms | Wave |
| 4 | 처치 + 도주 = 스폰 (수지) | Spawner |
| 5 | 챕터 카드 3장 추첨: 중복 없음, 모두 풀에서 추출 | Meta |
| 6 | `streak ∈ [0,7]`, `coinMultiplier = 1 + 0.2 × streak` | DailyStreak |
| 7 | 동일 seed → 동일 wave/spawn 시퀀스 (결정론) | SeededRandom |

추가: Power-up 동시 활성 ≤ 2 / Boss HP 곡선 (1.0/1.5/2.25/3.10/3.84).

```ts
import { fc, test } from '@fast-check/vitest'
import { Score } from '@/domain/score/score'

test.prop([fc.nat({ max: 100_000 })], { seed: 42, numRuns: 1000 })(
  '[Boundary] score ≥ 0 always — add any natural number, never negative',
  (n) => {
    const s = Score.zero().add(n)
    expect(s.value()).toBeGreaterThanOrEqual(0)
  },
)
```

### 결정론 강제: FakeClock + SeededRandom

```ts
// tests/fakes/fake-clock.ts
import type { IClock } from '@/domain/ports/clock.port'

export class FakeClock implements IClock {
  private t = 0
  now() { return this.t }
  monotonic() { return this.t }
  advance(ms: number) { this.t += ms }
}

// 사용
const clock = new FakeClock()
const combo = new Combo({ clock })
combo.incrementOnKill()
clock.advance(1499)
expect(combo.tier()).toBe(1.5)  // [Boundary] 1499ms = 유지
clock.advance(2)
expect(combo.tier()).toBe(1)    // [Boundary] 1501ms = decay 발생
```

## Alternatives

| 대안 | 거부 이유 |
|------|----------|
| **Happy path만 작성** | 회귀 위험 폭증. Master Plan §1.3 명시적으로 금지. PR review에서 차단 |
| **Snapshot test 중심** | 의도 없는 변경에 깨짐. game state 직렬화 비효율 |
| **E2E 위주 (Pyramid 역전)** | Playwright 30초/케이스 × 50 케이스 = 25분. CI feedback loop 망가짐 |
| **Mutation 미채택 (line coverage만)** | "100% line 100% useless" 안티패턴. assertion 없는 테스트도 100% line이 됨 |
| **Stryker 외 Mutation 도구** (PIT, Mutmut) | TypeScript / vitest runner 통합 약함 |
| **Property-based 미채택** | 결정론 강제 검증 불가능. Score invariant 등 손으로 1000회 케이스 작성 불가능 |

## Consequences

### 긍정적

1. **자율 실행 안전망** — 3 카테고리 + property + mutation 통과 = 사용자 개입 없이 회귀 차단
2. **결정론 검증** — seed=42에서 항상 동일 결과 → 디버그 재현 가능
3. **Domain 100% 강제** — 60초 envelope 안의 모든 분기 (combo tier, spawn rate, drop rate)가 테스트됨
4. **Ethics 강제** — `Notification.requestPermission` 호출 시 mutation에서 noop으로 변경되더라도 테스트 통과 → 코드 상 호출 자체 부재 강제

### 부정적

1. **테스트 작성 비용 증가** — `[Happy]/[Boundary]/[Error]` × 모든 SUT = 작성 시간 ~30% 증가
2. **Stryker 실행 시간** — domain ~30개 파일 → 약 5분 (incremental 모드로 완화)
3. **fast-check 학습 곡선** — `fc.property`, `arbitrary` 등 학습 필요 (Bible §3 시퀀스 검증에 필수)

## 12살 비유 (Kent C. Dodds 인용)

> 자동차를 만들 때 **시동 거는 부분(Happy)** 만 테스트하면 안 됩니다.
> **연료 0일 때(Boundary)**, **연료가 -10일 때(Error)** 도 함께 테스트해야 진짜 안전한 차입니다.
>
> 좀비팡에서:
> - **Happy** = 좀비 잡으면 점수 +100
> - **Boundary** = 정확히 5킬째 콤보가 ×1.5 되는지, 1499ms vs 1500ms decay 경계
> - **Error** = localStorage가 꽉 차 있을 때, 좀비 도주가 음수일 때, Vibration 없는 기기에서
>
> Property-based는 **무작위 1000번 시험** — "어떤 입력이든 점수는 음수가 안 되는지" 1000번 다른 입력으로 확인.
> Mutation은 **테스트 자체를 의심** — 코드의 `>=`을 `>`로 바꿔봤을 때 테스트가 실패하는지 확인. 통과하면 그 테스트는 의미 없음.
